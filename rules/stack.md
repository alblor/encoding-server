# Stack and architecture as it exists today

Last verified against the repo: 2026-10-31 (upstream release v1.0.0 plus the uncommitted restoration work, branch `feature/restoration-pipeline`). Target release v1.1.0 with the API string 2.1.0-secure, after QC; the bump is already in the tree (`api/main.py`, `api/app/documentation.py`).
Everything here describes code that is in the tree now. Design and status of the restoration feature: `rules/restoration-design.md`.

## Why the server looks the way it does

The server was built to encode private family media (VHS digitalizations, old videos) on hardware the owner does not fully trust, so the whole design starts from one rule: media is never written to a persistent disk. Everything is held in tmpfs, keys live in Redis memory, secrets arrive as Docker secrets, and the container is stripped of every privilege FFmpeg does not need. The API is the only component that ever touches plaintext media.

## Components

- `secure-encoding-api` (`api/`): FastAPI app on HTTPS 8443 (HTTP is disabled). Entry point `api/main.py`.
- `redis-secure`: password-protected, tmpfs `/data`, no published port, `expose: 6379` only.
- `secure-test-client`: opt-in compose profile `testing`, built from `client-tools/Dockerfile.secure`.
- Network `secure-encoding-net`: bridge, `172.30.0.0/16`, not `internal` (the API must be reachable).

## Application modules (`api/app/`)

`secret_manager.py` loads Docker secrets (fallbacks: `/secrets` volume, tmpfs, local dev). `config.py` builds `Settings` from env plus secrets. `encryption.py` is `EncryptionManager`. `secure_memory.py` is the encrypted virtual memory (RAM below the threshold, encrypted memory-mapped swap in tmpfs above it). `secure_jobs.py` is `SecureJobProcessor`: job lifecycle, FFmpeg execution, progress, cancellation, secure delete. `ffmpeg_validation_config.py` is the parameter whitelist (`libsvtav1` and other AV1 encoders are allowed). `ffmpeg_progress.py` parses FFmpeg progress. `tls_config.py` handles certificates. `documentation.py` serves the `/v1/docs` man pages. `jobs.py` still provides `FFmpegValidator` (imported by `secure_jobs.py`) and a legacy `JobProcessor` used by unit tests.

11 application routes: `GET /`, `GET /health`, `GET /v1/security/status`, `GET /v1/security/tls-status`, `GET /v1/presets`, `POST /v1/encryption/keypair`, `POST /v1/jobs`, `GET /v1/jobs`, `GET /v1/jobs/{job_id}`, `GET /v1/jobs/{job_id}/result`, `POST /v1/jobs/{job_id}/cancel`. The README says "21 endpoints, 12 processing"; the grep gives 20 (see MIN-021). The docs module documented 8 main endpoints and a test asserted exactly that; it now also documents the 8 restoration endpoints (`restore_*` ids), generated from the recipe schema, and the test file was extended, so keep module and test in step.

## Security model today

- Container: `no-new-privileges`, `cap_drop: ALL` then only `SETUID`/`SETGID`, `read_only: true`, AppArmor profile `ffmpeg-isolated`, seccomp `security/seccomp/api-server-minimal.json`, `ipc: none`, `mem_swappiness: 0`, `restart: "no"`.
- Memory: tmpfs `/tmp` 8g, `/tmp/memory-pool` 12g, `/tmp/encrypted-swap` 16g, `/var/tmp` 1g, all `noexec,nosuid,nodev`; container limit 32g.
- Secrets: five Docker secrets (`jwt_secret`, `encryption_master_key`, `redis_password`, `api_master_key` and, for the restoration workers, `restore_worker_redis_password`) from `./secrets/`, generated by `scripts/generate_secrets.sh`. `make secure-up` shreds them from the host once the container is up, `make secure-down` restores them.
- Encryption: `ENCRYPTION_MODE` defaults to `dual` (`automated` server-side, `manual` client-side with `client-tools/encrypt_media.py`). `off` exists only in the restoration recipe (`/v1/restore`); it skips the crypto layer, the media still lives only in RAM.
- Network exposure BEFORE commit 7c25bde (v1.0.0 plus docs): compose published `8443:8443` on 0.0.0.0, the bridge set `host_binding_ipv4: 0.0.0.0` and `ALLOWED_HOSTS` hard-coded a private LXC IP. Fine behind the Proxmox firewall in an LXC, open to the LAN elsewhere.
- ISSUE-028, committed in 7c25bde (it changes how the Mac reaches the server): `docker-compose.secure.yml` publishes 8443 on `${API_BIND_ADDR:-127.0.0.1}`, `ALLOWED_HOSTS` comes from `${ALLOWED_HOSTS:-localhost,127.0.0.1}`, the bridge `host_binding_ipv4` is 127.0.0.1, and a new `.env.example` holds placeholders. `docker compose config` renders loopback by default and the override works; NOT yet verified from a second host. To reach the API from the Mac, put the LXC address in `API_BIND_ADDR` and `ALLOWED_HOSTS` in the LXC's own `.env`. The old address stays in git history.
- Compose currently sets `pid: "host"` on the API service; the reason is not documented (INQUIRY-022).
- The documented guarantee is "no media on persistent disk", not "no files ever": model weights for the planned worker are public artifacts and are outside it (they may live on disk; the LXC rootfs was enlarged for them, ISSUE-030).

## Restoration feature as built (2026-10-30, uncommitted, QC pending)

- API half: `api/app/restore/` serves `/v1/restore/{presets, recipe/resolve, jobs, jobs/{id}, jobs/{id}/download, jobs/{id}/cancel, capabilities}` and `DELETE jobs/{id}`; job state in the existing `redis-secure`, media in the `restore-work` tmpfs volume (RAM). The API keeps the keys and does all crypto; the worker never sees a key. Job protocol: `rules/restore-job-protocol.md`.
- Worker half (ISSUE-012, built): `restore-worker/Dockerfile.gpu` is a glibc image because CUDA does not run on musl. It runs on `restore-net`, an `internal: true` network where Redis is the only reachable service (no egress, no route to the API port). Hardening: `read_only`, `cap_drop: ALL` with only `SETUID`, `SETGID`, `CHOWN` added, `no-new-privileges`, `ipc: none`, `mem_limit` and `memswap_limit` 22g, `restart: "no"`, runtime `nvidia`. The workers log in to Redis as the restricted ACL user `restore-worker` (only the `restore:queue/job/cancel/worker` keys and the commands `brpop hset hgetall get expire ping client|setinfo`, tested against a real Redis), so a compromised ffmpeg cannot read an encryption key. The Redis and worker entrypoints refuse a `SHREDDED_FOR_SECURITY` marker as a password. A root entrypoint copies the worker's Redis secret to tmpfs, hands it to uid 10001 (mode 0400) and drops every privilege with `setpriv` before Python starts. Compile caches (not media) and weights (public artifacts, mounted read-only) may live on disk.
- Profiles: the workers (`restore-worker-gpu0`, `restore-worker-gpu1`) are in compose profile `gpu`; the default stack renders unchanged. Start and stop them with the Makefile `gpu-*` targets so the secret lifecycle (shred after start-up) still applies.
- Owner scoping: jobs belong to the SHA-256 of the `X-API-Key` header. That is isolation between callers, NOT authentication: the existing API has no authentication at all (ISSUE-054; the `/v1/docs/auth` text says otherwise, MIN-112; a YubiKey option is researched in INQUIRY-111). Manual-mode uploads are decrypted by streaming; the password is kept wrapped by `EncryptionManager`. Cancel and delete are two-phase, the job directory is overwritten 3 times before unlink.
- Open checks: from a second host the port is not reachable (ISSUE-028); the `su-exec` group for gid 10001 inside the real API container (MIN-055: fixed as `su-exec 1000`, to confirm after the deploy); a real deploy on the server (FEATURE-009).
