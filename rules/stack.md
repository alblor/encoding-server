# Stack and architecture as it exists today

Last verified against the repo: 2026-10-29 (upstream release v1.0.0, branch `feature/restoration-pipeline`).
Everything here describes code that is in the tree now. Planned work lives in `rules/restoration-design.md`.

## Why the server looks the way it does

The server was built to encode private family media (VHS digitalizations, old videos) on hardware the owner does not fully trust, so the whole design starts from one rule: media is never written to a persistent disk. Everything is held in tmpfs, keys live in Redis memory, secrets arrive as Docker secrets, and the container is stripped of every privilege FFmpeg does not need. The API is the only component that ever touches plaintext media.

## Stack

| Layer | What | Version / source |
|---|---|---|
| Language | Python | 3.11 (`python3=~3.11` on Alpine) |
| API | FastAPI + uvicorn | 0.104.1 / 0.24.0 (`api/requirements.txt`) |

`api/requirements.txt` also pins pytest, black 23.11.0, isort, flake8 and mypy; they ship in the image today. Dependency bumps are a security task, see `rules/conventions.md`.

## Components

- `secure-encoding-api` (`api/`): FastAPI app on HTTPS 8443 (HTTP is disabled). Entry point `api/main.py`.
- `redis-secure`: password-protected, tmpfs `/data`, no published port, `expose: 6379` only.
- `secure-test-client`: opt-in compose profile `testing`, built from `client-tools/Dockerfile.secure`.
- Network `secure-encoding-net`: bridge, `172.30.0.0/16`, not `internal` (the API must be reachable).

## Application modules (`api/app/`)

`secret_manager.py` loads Docker secrets (fallbacks: `/secrets` volume, tmpfs, local dev). `config.py` builds `Settings` from env plus secrets. `encryption.py` is `EncryptionManager`. `secure_memory.py` is the encrypted virtual memory (RAM below the threshold, encrypted memory-mapped swap in tmpfs above it). `secure_jobs.py` is `SecureJobProcessor`: job lifecycle, FFmpeg execution, progress, cancellation, secure delete. `ffmpeg_validation_config.py` is the parameter whitelist (`libsvtav1` and other AV1 encoders are allowed). `ffmpeg_progress.py` parses FFmpeg progress. `tls_config.py` handles certificates. `documentation.py` serves the `/v1/docs` man pages. `jobs.py` still provides `FFmpegValidator` (imported by `secure_jobs.py`) and a legacy `JobProcessor` used by unit tests.

## Routes in `api/main.py`

11 application routes: `GET /`, `GET /health`, `GET /v1/security/status`, `GET /v1/security/tls-status`, `GET /v1/presets`, `POST /v1/encryption/keypair`, `POST /v1/jobs`, `GET /v1/jobs`, `GET /v1/jobs/{job_id}`, `GET /v1/jobs/{job_id}/result`, `POST /v1/jobs/{job_id}/cancel`. Plus 9 documentation routes under `/v1/docs` (index, overview, modes, endpoints, endpoints/{endpoint_id}, auth, examples, errors, tools). The README says "21 endpoints, 12 processing"; the grep gives 20 (see MIN-021). The docs module itself documents 8 main endpoints and a test asserts exactly that, so do not change the count casually.

## Security model today

- Container: `no-new-privileges`, `cap_drop: ALL` then only `SETUID`/`SETGID`, `read_only: true`, AppArmor profile `ffmpeg-isolated`, seccomp `security/seccomp/api-server-minimal.json`, `ipc: none`, `mem_swappiness: 0`, `restart: "no"`.
- Memory: tmpfs `/tmp` 8g, `/tmp/memory-pool` 12g, `/tmp/encrypted-swap` 16g, `/var/tmp` 1g, all `noexec,nosuid,nodev`; container limit 32g.
- Secrets: four Docker secrets (`jwt_secret`, `encryption_master_key`, `redis_password`, `api_master_key`) from `./secrets/`, generated by `scripts/generate_secrets.sh`. `make secure-up` shreds them from the host once the container is up, `make secure-down` restores them.
- Encryption: `ENCRYPTION_MODE` defaults to `dual` (`automated` server-side, `manual` client-side with `client-tools/encrypt_media.py`). No `off` value exists yet (planned, FEATURE-004).
- Network exposure, committed state (v1.0.0 plus docs): compose publishes `8443:8443` on 0.0.0.0, the bridge sets `host_binding_ipv4: 0.0.0.0` and `ALLOWED_HOSTS` hard-codes a private LXC IP. Fine behind the Proxmox firewall in an LXC, open to the LAN elsewhere.
- ISSUE-028, implemented in the working tree and NOT committed (awaiting the owner's go, since it changes how the Mac reaches the server): `docker-compose.secure.yml` publishes 8443 on `${API_BIND_ADDR:-127.0.0.1}`, `ALLOWED_HOSTS` comes from `${ALLOWED_HOSTS:-localhost,127.0.0.1}`, the bridge `host_binding_ipv4` is 127.0.0.1, and a new `.env.example` holds placeholders. `docker compose config` renders loopback by default and the override works; NOT yet verified from a second host. To reach the API from the Mac, put the LXC address in `API_BIND_ADDR` and `ALLOWED_HOSTS` in the LXC's own `.env`. The old address stays in git history.
- Compose currently sets `pid: "host"` on the API service; the reason is not documented (INQUIRY-022).
- The documented guarantee is "no media on persistent disk", not "no files ever": model weights for the planned worker are public artifacts and are outside it (they may live on disk; the LXC rootfs was enlarged for them, ISSUE-030).
