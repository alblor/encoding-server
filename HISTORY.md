The owner answered the blur question and watched the new render. For INQUIRY-106 the answer is bloom only, inferred from the original, with no conditional or defocus logic: "the model should improve the details anyway", and "it should be adapting to the movie source itself, and in this case it wasn't much to restore". So the focus-aware softening I had sketched is dropped, and the glow stage (MIN-102) does the job: `cleanup-4k` now sets `fidelity.glow` 1.0 in `restore_core/recipe.py`, on top of fp8. v9 was rendered on both GPUs, since the owner freed GPU 0: 23 segments, 1896 frames, about 26 min wall against 52 min for v8 on one GPU, 170.06 MB against 170.02 MB. Against v8 it is identical to 4 digits elsewhere, the restored light near highlights on frame 900 is already above the source (0.048 mean linear-light surplus), and the clip-wide luma moves by +0.07 on about 138. So v9 looks like v8 on this film, and glow is a floor for films where the model tightens the bloom. He approved it ("that's what I was looking for"). `plateau_purge` stays opt-in (IDEA-105 open).

The owner's rule for the deploy was "only if QC is 4.8/5 or better, otherwise fix first", so the quality-control engineer scored the tree with a numeric rubric (5.0 minus 1.0 per critical, 0.5 per high, 0.1 per medium, 0.02 per low, 0.1 per unverified area). Around it: a macOS `dd` fallback that got `count= 44`, an "encrypted backup" whose random passphrase was thrown away (an archive nobody could open, with the passphrase visible in `ps`), `generate_secrets.sh` printing the first 8 characters of each secret, `needs_source` leaving out glow (the same class of bug as BUG-091), and a valid but wrong ONNX as `HEAD_MODEL` failing with a cryptic broadcast error. Round 2 scored 4.66 after the fixes and found that nothing created or chowned the compile-cache bind directory, so the first job on a clean host would have died with a `PermissionError`, plus gaps in `docs/DEPLOY_PROXMOX.md` and a `gpu-status` that curled localhost while the API binds `API_BIND_ADDR`. Round 3 scored 4.80 and passed with no findings. That is the gate met with zero margin, because one more LOW finding would have made it 4.78. The fixes are in BUG-113 to BUG-115 (`rules/roadmap-outcomes-2.md`); the tests went from 211 to 215 on the host and from 130 to 138 on the worker, all passing.

What QC could not verify stays open for the deploy trial, and I want that to be clear, since the pass does not cover it: the AppArmor profile needs a real AppArmor host (INQUIRY-116), and the GPU image needs the real server for the `setpriv --bounding-set=-all` entrypoint under no-cgroups, the worker's Redis ACL login, `worker.py` end to end, and a `make gpu-build` of the current `Dockerfile.gpu`, which is newer than the image the GPU evidence came from (INQUIRY-117). I also did not promote the other `review` rows to `complete` in this pass; see `rules/resume-checklist.md`.

The owner's conditional go is satisfied by the 4.80, so the v1.1.0 merge, the tag (internal version 2.1.0-secure) and the non-destructive deploy start right after this pass. FEATURE-060 is therefore in progress, not done, and a final entry will follow with the outcome.

The second thread is authentication. The API has none today: `X-API-Key` only scopes jobs by its hash, and the only gates are TLS and `API_BIND_ADDR`, while the `/v1/docs/auth` text talks about JWT and an API-key system that is not there (MIN-112). The owner does not want to create credentials, and asked whether every API call could be authorized by a manual press on his YubiKey, so that when he asks the agent to re-encode a movie the call first waits on the key. A research agent went through python-fido2, py_webauthn, the Yubico and WebAuthn and CTAP specs and the OpenSSH sk docs: it is feasible, with no blocker. The design is a non-resident ES256 credential, `user_verification="discouraged"` on both begin calls (the trap is that `preferred` raises `CONFIGURATION_UNSUPPORTED` when the key has no PIN), one touch for a short-lived token and not one per call, since a film is hundreds of calls. Nothing was run on hardware, no key was plugged into the Mac, and nothing is built: INQUIRY-111 waits for the owner's go, and any change to authentication after the deploy needs a new QC pass. Everything is in `rules/yubikey-auth-inquiry.md`.

Left as it was, on purpose: the SparkVSR-dependent INQUIRY-010, INQUIRY-033, IDEA-034 and IDEA-039 stay open for the owner to close, MIN-021 (README recipe docs) is still open, and the undervolt and thermal follow-ups (MIN-108, MIN-109, INQUIRY-110) wait for the end phase.

## 2026-11-03 - The 5080s get a certified undervolt and a fan policy, and the host goes back to how it was (MIN-037, campaign 2026-11-01 to 2026-11-03)

Roadmap: complete MIN-037 (GPU thermals, undervolt and fan policy, was P4 planned); new MIN-108 (reboot test of the boot ordering, planned), MIN-109 (re-validate the profile after a driver update, planned), INQUIRY-110 (promote the campaign tooling out of the gitignored sandbox, planned, waits for the owner).

MIN-037 was the item parked at the very end of the project, and it started from a plain number: on 2026-10-30 GPU 1 was sitting at 87 °C with 100% fan under dual load, while GPU 0 stayed far cooler. The owner did not want to chase the silicon lottery for +10-15% speed, they wanted a very stable configuration that keeps the core voltage low during the long jobs, with less power and less thermal stress on both cards. Between 2026-11-01 and 2026-11-03 I ran the campaign on the host (driver 580.76.05, same VBIOS on both cards, both GPUs loaded at the same time like in production) and every config had to pass the same gate: idle soak, a matmul check where every iteration is bit-identical to stock, load/idle bursts, ReCaVSR on a real segment with the output compared to stock, Blender Cycles OptiX, and no Xid in the host kernel log. Anything less was a FAIL.

The first thing the campaign taught was that the obvious tool does not work on both cards. GPU 0 takes the documented NVML controls (power limit, clock lock, offset), though a lock applied with +420 or more throws Xid 62 at idle, which cost host reboots. GPU 1 cannot use a clock lock at all, since even at +0 it corrupted 2 load/idle transitions out of 66. So GPU 1 moved to a V/F curve flatten written through the undocumented NvAPI, which gave the result of the lock without the lock (496 transitions, 0 bad), and the same curve on GPU 0 landed on the lock's numbers to the MHz, hence the certified profile uses the curve on both. The price is that it only runs on the driver it was validated on, and the unit falls back to stock on any other driver or any failed read-back.

The pick came from the owner reading the rounds: power limit 300 W and the curve flat at 2850 MHz with +450 below it, on both cards. Before certifying it they asked how far it sits from the instability, so I probed +470, +480 and +490 at the same top and a 2900 top. All passed, the only failure ever seen is +500 unlocked on GPU 1 (a ReCaVSR hang and a lost GPU), and 2900 costs 4-13 mV more on the long load, which is the thing this campaign is for, hence 2850 +450 stayed. The certification took 4 h 15 min with every test PASS and 0 Xid (30 min matmul, 130 load/idle bursts, 30 min gpu-burn, memtest_vulkan, 2 h of ReCaVSR with 206 of 206 rounds identical to stock). Against stock that is 22-25% less energy per frame on ReCaVSR, 110-122 mV less core voltage, 2-5% faster matmul and 0.3-1.7% faster ReCaVSR, and it sits 40 MHz under +490.

GPU 1's heat turned out to be the stacking, not the card. With GPU 0's fans forced to 100%, GPU 1 at the same 300 W went from 84 °C to 74 °C, and at the same clock and voltage it does not draw more power than GPU 0. For production the owner chose the fan behavior: the stock curve + 15 points on both cards, zero-RPM kept up to 39 °C, a cool-down ramp that gets longer with each temperature decade, and every card at 85% or more while any card is above 82 °C. The driver has no fan curve offset, so it is a software curve, and because a manual fan speed outlives the process that set it, the unit is `Type=notify` with a watchdog and an `ExecStopPost` that hands the fans back to the firmware. I want to be precise about what was tested: the 4 h 15 min certification ran with GPU 0's fans forced to 80% (85% once GPU 1 reached 85 °C), not with this policy. The policy has a screening round (f01, PASS on both cards, GPU 1 peaked at 84 °C), two live fan tests and the crash tests (`kill -9`, a frozen loop, `SIGTERM`, manual fans left at startup), and all of those end with the cards back on auto.

It was installed on the host at 20:33 the same day: `gpu-profile.service` (oneshot, before the guests start) and `gpu-fan-policy.service`, scripts in `/opt/gpu-profile`, settings in `/etc/default/gpu-profile`, profile verified, 0 Xid. The exact installed files plus checksums and a README are kept as a restore kit in the owner's HomeLab folder for the host. Then the teardown, because the campaign had its own temporary access: the sshd `Match` block and the key line were reverted (root SSH from the Mac is refused again), the key shredded, `/etc/sudoers.d` checked and untouched, the temp folders on the host and in the LXC removed after copying the logs and telemetry out, the `gpubench` image removed, and `/dev/shm/media` left alone. The evidence stays in the gitignored `tools/sandbox/gpu-tuning/` (the report and `results/`), and the operational summary is in `rules/gpu-undervolt.md`.

What is not done: the boot ordering has never been tested with a real reboot, since a reboot wipes the media in the LXC's RAM, so it waits for the next planned one (MIN-108). After any NVIDIA driver update the profile stays at stock by design until it is re-validated (MIN-109). And the campaign tools live only in the gitignored sandbox, so a clean checkout could not repeat the validation: whether to promote them is the owner's call (INQUIRY-110). One sub-task of the old MIN-037 text, checking GPU 0's PCIe gen4 x8 link, was never covered by the campaign, and I put it under MIN-108 so it does not get lost.

The head tracks (FEATURE-100) came from one shot at 0:33 to 0:36, where a person seen from behind had plastic, messy hair: the same kind of problem as the wrong eyes on a small face, though here the face detector has nothing to find. `restore_worker/heads.py` runs a YOLOX person detector (OpenCV model zoo, Apache-2.0, 36 MB) over the source in half-size 640 px tiles, because a person 100 px tall at 2160p is only 17 px if you shrink the whole frame to 640, derives a head box from each person box and hands it to the same zoom stage that redraws faces. A head track that overlaps a face track is dropped, the stage runs only with `face_guard: zoom`, and it is optional: no model file, no stage, no error. The model is staged and SHA-256 checked by `scripts/stage_restore_weights.sh`, and the worker reads it from `HEAD_MODEL`. On v8 that segment got 1 head track and 79 zoomed frames.

Two finishing stages came out of the owner's last notes, and both are opt-in because the measurements did not justify more. The glow stage (MIN-102, `fidelity.glow`, default 0) adds back the original's bloom around bright lights in linear light, additive only: my first version also took light away, and it turned one lamp core red and dark. Measured on frame 900, v8's halo falloff is already about 93% of the original's and glow adds about 1%, so no preset enables it. The plateau purge (MIN-103, `bitdepth.plateau_purge`, default 0) touches only wide staircases, which means banding and posterised contour patches. A background agent compared it against the alternatives on synthetic degradations of clean v8 frames: banding curvature went from 0.051 to 0.027 with a textured-area change of 0.006 to 0.016 codes, while the existing deband changed 81 to 87% of a clean frame, FBCNN lost high-frequency detail (ratio 0.81 to 0.95), ffmpeg's gradfun, deband, spp, fspp, uspp and deblock were rejected, ring suppression did nothing and gated deblocking was safe but modest. Blocking and ringing of low-quality encodes cannot be removed conservatively, and on the real draft the purge is a near no-op (dark flat-pixel share 0.338 against 0.344), so it waits for a damaged source (IDEA-105). The honest caveat is that this evidence is synthetic plus eyeballed sheets, no real damaged film yet. 6 and 5 tests respectively; peak VRAM unchanged at 9.67 GiB allocated.

The face research is closed too. SparkVSR as a face engine is not better than the zoom (INQUIRY-101): without a reference the face is blurry with hollow eyes, it only matches the zoom when it is fed the zoom's own key-frames, the flicker is not better, and it costs about 0.8 s per frame, 37 GiB of RSS and 90 s extra per 80-frame track (a 256 px by 81-frame crop ran out of memory). The VACE retest with the masked protocol gave an SFace identity of about 0.55 against 0.35 for the zoom with one reference on the 1.3B model, but it is fragile (three references were worse, a hard cut fails, the seed changes the result, 14B in Q4 takes 6 to 7 min per clip) and the owner dropped it. KEEP was already rejected. With his approval the SparkVSR weights, code, image and scratch were deleted from the server (MIN-107); the worker image, the recavsr weights with `yunet.onnx` and `yolox.onnx`, `/srv/src/code` and the RAM scratch stay. That quietly parks INQUIRY-010, INQUIRY-033, IDEA-034 and IDEA-039, which need SparkVSR staged again, and I wrote that under MIN-107. MiniMax-H3 was NOT researched (the licence excludes the EU, it is 33B, parts are hosted-only) and it will be only if he asks. GPU 0 on the server is his own benchmark, so sessions use GPU 1 only: it is now a standing rule in the reminders.

One question is open and I did not answer it for him (INQUIRY-106). He asked for a "dynamic" way to understand the "blur overlay" of the original and re-apply it. I measured the obvious reading first and it is not the bloom. What differs is that the original's out-of-focus lamps and candles are soft orbs while the model gives them filament detail (restored over source band energy 1.1 to 1.5x, up to 3x at edges). A candidate design is focus-aware softening that follows the original frame by frame, a per-region sharpness limit with a better focus measure than the fine over mid energy ratio, which was too noisy because of the source's compression noise. It fits one meaning of his sentence though, and there may be another, so it waits until he says which.

State at the end of the day: 211 host tests and 130 CPU-worker tests pass (reported by the session, not re-run by me). The merge gate is still open and wider than before: the QC re-check (ISSUE-059) has to cover `heads.py`, the face stage in `pipeline.py`, glow, plateau purge, the tone and tracker fixes, and the earlier ISSUE-059 fixes. ## 2026-10-31 (late night) - QC run 5 fails on a silent corruption, run 6 passes with concerns, the encoder was the one flattening the shadows, and the owner picks the face zoom

Roadmap: new BUG-091 (QC run 5 critical and high), BUG-092 (run 5 medium and low), BUG-093 (run 6 medium), MIN-094 (run 6 low leftovers, planned), FEATURE-095 (shadow texture), IDEA-096 (10-bit path through the model, postponed), MIN-097 (`face_zoom_mix` and zoom as the preset), FEATURE-098 (face tracker: shot cuts and fast faces), INQUIRY-099 (MiniMax-H3 and Bernini, planned); INQUIRY-086 complete (the owner answered: zoom, 20/80 mix); INQUIRY-088 to progress (the VACE retest is running); ISSUE-059 from progress to review, still the merge gate. Nothing is committed, `main` is untouched. Details: `rules/restore-qc.md` (the early runs moved to `rules/restore-qc-early.md`), `rules/restore-shadow-texture.md`, `rules/restore-face-guard.md`, `rules/restore-research.md`.

Run 5 said FAIL, with one critical finding, and it is the kind I like to have written down: a copy cut of an mkv whose video starts 6 s or more after its audio silently corrupts frames, because ffmpeg's default probe window is 5 s and a video that begins later is simply not seen when the file is opened. The same run had a high one (`needs_source` left out adaptive and match softening and any `face_guard` other than off, so the worker never received the source those stages need) and a handful of mediums: the zoom output was not validated, the guard weight popped at the ends of a track, cancel and report were blind during the face stages, a corrupt face model gave a raw `cv2.error`, and the tone clamp. All fixed: one `PROBE` constant (`-analyzeduration 60000000 -probesize 100000000`) now sits before every source `-i` in the client and in `probe_media.py`, the decode passes `-fps_mode passthrough`, `needs_source` is complete, both the zoom output and the main engine output are validated, the ramp reaches exactly the first and last detection weight, cancellation is checked between detections and tracks, and an unreadable model raises `FaceModelMissing`. Run 6 then came back PASS WITH CONCERNS, no critical and no high, after 12 lead-in cases (0.4 to 20 s, AAC and PCM audio), VFR inputs, a libdav1d and libaom decode of the encodes made with ac-bias and quant matrices, and a memory envelope that held within 3%. Its mediums are fixed too: the tone curve is bounded on the white side as well (contrast * pivot and contrast * (1 - pivot) at 0.15 or below), a weak detection can only link to a track within 2 face sizes (a lamp could hijack a face track), non-finite detection rows are dropped, duplicate tracks are merged, and a failed client assembly deletes the rejected output file. The low ones I left open on purpose (MIN-094): crossing faces swap track identity, VFR with real timestamp gaps fails closed only at assembly, jittered VFR with duplicate pts is refused at preflight (a false positive), a video late against a subtitle track with no audio is delayed twice (fail-closed), and the cpu compose service has no `/m` mount. Tests are 211 on the host and 115 in the CPU worker image. What I could not do: nobody has looked at the fixes made after run 6, so ISSUE-059 needs one short QC re-check or the owner's explicit acceptance before the merge, and I did not receive the list of the run 5 low findings, so BUG-092 says so.

The owner then wrote that the textures from the original look flattened and lack dynamic range, and that he wants to keep the warm cinematic blur, not a flat picture. I measured it on the 0:52 to 0:54 shot (24 frames, restored with the real engine) and the answer was not where I expected: before the AV1 encode only 0.9% of the dark pixels (source luma under 25/255, which is 80.7% of that picture) sat in flat plateaus, after the default encode 34.1% (source 62.1%), so it was the encoder, not the model and not the finishing stage, that flattened the shadows. Twelve variants later (the table is in `rules/restore-shadow-texture.md`) the recipe I chose is deband off, `grain.shadow_weight` 0.35 (new field, default 0.12), `encode.ac_bias` 1.0 and `encode.quant_matrices` true (new, defaults 0 and false), set in `cleanup-4k` and `film-restoration` through the constant `SHADOW_TEXTURE`. On the whole draft (v7 against v6) the dark-pixel plateaus go from 83.6% to 33.2% (source 76.9%) and the fine band RMS from 0.89 to 0.96, at the price of a file that grows from 99.6 MB to 171 MB (+72%, about 17 Mb/s on a very dark film), which is why the owner can trade texture for bits with `shadow_weight` or `ac_bias`. Two things worth keeping from the search: ffmpeg silently accepts unknown `-svtav1-params` names unless you run with `-v warning` (valid in SVT-AV1 4.2: ac-bias, enable-qm, qm-min, variance-boost-strength, luminance-qp-bias, sharpness, tf-strength, enable-restoration; invalid: variance-boost-octile, noise-norm-strength, psy-rd, spy-rd), and the pipeline decodes to 8-bit RGB and the model outputs 8-bit, so the 10-bit shadow precision of a source is lost at the model stage, a known limit I did not change (IDEA-096).

On the faces, the owner chose `face_guard: zoom` with a 20/80 mix of the original and the redrawn face (`fidelity.face_zoom_mix` 0.8, preset `cleanup-4k`), so INQUIRY-086 is closed. The tracker got better in the meantime (FEATURE-098): it stops at hard cuts inside a segment (64x36 thumbnails, mean change above max(24, 5x the median)), and it follows fast faces with a wide link gate of 8 face sizes for confident detections and a cost of distance + 3*log(size ratio) - 3*score - 4*IoU, while weak detections link within 2. I simulated the two abrupt cases on the draft through the real worker (sheets in `~/Downloads/restoration-comparison/draft_movie/abrupt/`): a hard cut into a shot where the 45 px face is already visible is redrawn from the first frame of the new shot, and a fast digital zoom-in (4x in 24 frames, face 45 to 180 px) lost the face in my first tracker, since it moved more than a face width per frame and the IoU linking failed, so the first frames stayed uncanny, until the wide gate fixed it. The drafts v5 (preset, guard on), v6 (zoom) and v7 (final recipe, whole draft) are in `draft_movie/`.

Face research moved too, and I wrote the verdicts in `rules/restore-research.md`. KEEP, tested on the server, is worse than the ReCaVSR zoom in every variant (a different face invented from the aligned 128 px input, waxy faces from the source, a frown on top of the zoom, 22 to 26% more flicker, a sticker-like face on the fast zoom-in, 13.1 GB of VRAM, and an NTU S-Lab non-commercial licence), so it is rejected. The first VACE test showed no effect of the references, and the research agent explained why (with the mask set to None the whole clip is a dense control), so a retest of the proper masked-inpainting protocol with white-background references, on 1.3B and on 14B with an SFace identity metric, is running now. MiniMax-H3 is real and open-weight, but its community licence excludes the EU, UK, Korea and the US, the open weights have no video-to-video and the technical fit looks weak: the owner asked me to research it, also on Reddit, only if the VACE retest fails, and I told him the licence point once. "Germini from ByteDance" is most plausibly Bernini (Apache-2.0, Wan-based), an inference I have not verified. Still waiting for him: the comparison of v7 and the abrupt sheets, and the grain reference clip (INQUIRY-058). The order of the rest is in `rules/resume-checklist.md`: the re-check or his acceptance, his go, commits through `git-scm-master`, push, merge to main only after the go, tag v1.1.0, deploy to the LXC without touching the old install, the 3-segment trial, the SSH teardown. ## 2026-10-31 (night) - QC run 4 passes with concerns, the finishing stage learns to keep the source's details, and small faces get a guard

Nothing is committed, `main` is untouched.

The QC engineer came back twice more. Run 3 said FAIL on two high client findings (the audio and video desynchronise when the video starts after the audio, and an `IndexError` in `plan_segments`), they were fixed, and run 4 said PASS WITH CONCERNS: two high (the `assemble()` duration check aborted a correct file when the video lead-in was more than about 0.5 s, and `video_start_delay()` returned 0 for a lead-in beyond ffprobe's probe window, which is a silent desync, the worst kind), four medium (`Dockerfile.cpu` did not copy `faces.py`, adaptive softening and local contrast crashed on tiny or very narrow frames, the tone curve flattened shadows when contrast * pivot went above 0.25, and the unset tone pivot steps at segment cuts) and three low. All fixed except the pivot seam, which I documented on purpose because tone is opt-in and an unset pivot is the scene median of each segment, and the low ones are listed in MIN-076 with the two points I could not confirm. The client now takes the delay from packet times and the plan duration from frame times, cuts open-GOP and start-offset sources by decoding and re-encoding them near-losslessly (CRF 8, closed GOP, `--cut auto|copy|transcode`), and the Makefile `secure-down` passes `--profile cpu --profile gpu` so the workers stop with the stack. Host suite 209 tests, CPU worker suite 100, run 5 is running. Details: `rules/restore-qc.md`.

On the picture, the owner kept asking for the same thing, which is to keep the model's detail where the original supports it and to stay faithful everywhere else, so the finishing stage got four new pieces: `fidelity.soften = adaptive` (a source-supported four-band luma limiter that never adds energy), a `tone` block (contrast, optional pivot, local contrast, saturation, with the contrast clamped so contrast * pivot stays at 0.24 or below), a colour anchor of 0.35 next to the brightness anchor of 0.9, and grain taken from the source's own residual for any source size (it keeps about 60% of the source grain amplitude and the default AV1 encode takes away about a third of that). ## 2026-10-30 - Engine decision: SparkVSR fails the speed gate, ReCaVSR becomes the leading candidate

Roadmap: INQUIRY-032 (complete), INQUIRY-029 (complete, continues as INQUIRY-038), FEATURE-006 (retitled), INQUIRY-017 (now per engine), INQUIRY-035 (new), INQUIRY-038 (new), IDEA-039 (new), INQUIRY-011 (ReCaVSR licence added), INQUIRY-010 (P1 to P2). Nothing committed; the numbers are in `rules/m3-benchmark.md` and `rules/recavsr-evaluation.md`.

The first benchmark left one question open: the CogVideoX VAE was about 87% of the SparkVSR runtime, so could it be sped up? The owner finds about 7 days per film too long, and his decision was that unless the VAE gets significantly faster the engine switches to ReCaVSR, provided that one is also state of the art in quality, with a full visual comparison (screenshots and draft videos) to show for it. The VAE spike (INQUIRY-032) answered the first half. The VAE alone costs about 626 ms per megapixel-frame (encode + decode, tile 512), about 659 at tile 768 and 691 at 1024, so a bigger tile does not help; fp16 is 634, no gain; with VAE tiling and slicing off it OOMs even at 512 px on an empty 16 GB card. `torch.compile` was NOT tested, since the runtime image has no C compiler and the VAE is conv-bound, so little gain is expected (IDEA-039, postponed). A 2160p frame is about 8.3 Mpx, so the VAE alone is about 5.2 s/frame/GPU. The gate I proposed was at most 3.0 s/frame/GPU (about 3 days per 2 h film on two GPUs), and even a 2x VAE gain would give about 3.5 s/frame, so SparkVSR cannot reach it. INQUIRY-032 is closed as "the VAE is not fixable", and SparkVSR is NOT viable as the primary engine for whole films at 2160p. It stays as an optional engine (`restore.engine: recavsr | sparkvsr | classical | none`).

The spike also turned up upstream problems that matter if the optional engine is ever built: the temporal chunk merge crashes after all the compute is done when the padded frame count leaves a short tail (F=361 with chunk 49 gives a 70-frame last chunk against 69 expected, and F=336 is padded to 337 and crashes the same way), so only counts of the form 49+41k with k a multiple of 4 work and a crashed run loses its results; it writes 16 fps by default; and it held up to about 45 GB of host RAM for a 213 to 336 frame 976x1660 clip.

ReCaVSR (arXiv 2609.37831, USTC, submitted 2026-09-29) is a one-step streaming diffusion model on Wan2.2-TI2V-5B with recycled latents and learned cache routing, and a 57M FlashDecoder instead of the VAE, which is exactly the part that sank SparkVSR. Everything quality-related in the paper is the authors' own claim: best DOVER on four sets, best LPIPS on two, 21.2 FPS at 1080p on an A100 against 0.56 for SparkVSR, though SparkVSR appears only in their speed table and in none of the quality ones. The repo was about 7 weeks old with 19 stars. The code is Apache-2.0 but the WEIGHTS LICENCE IS NOT STATED (no tag on Hugging Face, the README defers to the licences of the parts), so it went on INQUIRY-011. It needs its own environment (torch 2.10, CUDA 13.0 wheels, Python 3.13 in the venv) and ran fine on the RTX 5080 with the 580 driver in its own container, which needs gcc because Triton compiles a launcher.

Measured on one RTX 5080 with the demo clip (488x830, output 976x1660 = 1.62 Mpx): peak allocated 13.3 GiB, peak VRAM 15.4 GiB, so 1.62 Mpx is about the limit (scale 3 and scale 4 both OOM in the `lq_proj` streaming). The one-time compile costs about 100 s per process, then it runs at about 0.08 to 0.09 s/frame (about 11 FPS), with a host RAM peak of about 5.5 GB for 336 frames. The estimate for 2160p, scaled by area (5.1x), is about 0.4 to 0.6 s/frame, so about 12 to 14 h per 2 h film on two GPUs, 10 to 15x faster than SparkVSR; it is an ESTIMATE, and 2160p will need spatial tiles of about 1.6 Mpx. Since here the transformer dominates and not a VAE, FP8 would free about 5 GB of its 10.6 GB, so quantization finally matters for speed and for memory (INQUIRY-038).

The first quality comparison used ReCaVSR's own demo clip, which is modern, AI-looking footage and therefore home ground for ReCaVSR, NOT old film, at 2x, with SparkVSR in `no_ref` mode (not the authors' best, the PiSA-SR reference is still untested) and 49-frame chunks. On 213 frames the added flicker is 5.98 for SparkVSR against 5.07 for ReCaVSR (lower is better), sharpness (Laplacian variance) is 32 for Lanczos, 327 and 198, and LR-consistency PSNR is 25.0 against 27.8 dB. On the first 49 frames alone the faithfulness numbers flip (31.6 against 27.9 dB), so the two clips disagree and the longer one is the more reliable. SparkVSR has the lower median flicker (4.46 against 5.00) but bursts to 16 or 17 at the final chunk seam and around frames 192 to 196, while ReCaVSR peaks at 7.9 with no seam signature. By eye, on 1:1 crops, SparkVSR is crisper but painterly and posterised, with invented grit on asphalt and a face that drifts on at least one frame, and ReCaVSR is more natural and faithful, a bit softer; that is my reading, a first impression and not a verdict. A hard scene cut (48 frames of the demo, then unrelated letterboxed footage) showed no content bleed, only faint residue in the black bar on the first frame after the cut. The caveats are many: one clip, the authors' footage, proxy metrics, no real film yet and no TV A/B. The deliverables are on the owner's Mac in a `restoration-comparison` folder under Downloads.

FEATURE-006 was retitled "M3 Restore stage (engine-agnostic)"; it is the same milestone and the same component, only the engine became a recipe field, so I widened it instead of closing it and said so in its details (the old title is kept there). The benchmark also showed why the stock script cannot be the production path. The model does not fit in 16 GiB (transformer about 11 GB plus T5 about 9.5 GB OOM at load); a cached empty-prompt embedding lets the pipeline load with `text_encoder=None`. Even then the resident transformer leaves no room for the VAE, so the design answer is stage-major scheduling (the owner suggested serial load/offload loops): transformer on all tiles, one offload (pinned memory should bring an 11 GB move to about a second, the 4-5 s measured was pageable memory), then the VAE. Since the transformer is only about 13% of the runtime, quantization buys at most a few percent end to end, and stage-major scheduling already solves the memory side with no quality risk. ## 2026-10-29 - Research findings behind the plan

Roadmap: INQUIRY-002, INQUIRY-010, INQUIRY-011, INQUIRY-015, INQUIRY-017, MIN-016.

SparkVSR is built on CogVideoX1.5-5B and does one transformer pass per window (`sr_noise_step=399`). It is CUDA-only (`pipe.to("cuda")`), so no Mac. The only speed figure found is 588 s for 48 frames at 3456x1920 output on an RTX 3090, with 28 tiles of 512x512, about 12 s per frame (corrected later the same day: it is a community report, issue #28, and the paper itself gives no timing). Extrapolated to a 2 h film at 2160p that is roughly 15 days on two GPUs, an upper bound from different hardware and not a measurement, which is why the measured ETA from M3 became an exit criterion (INQUIRY-017). VRAM figures: 29 GB for 32 frames 270p to 1080p on an A100 untiled, 14.9 GiB allocated peak for the tiled 3090 run, and the RTX 5080 has 16 GB.

The upstream inference script could not be used as it stands: it bilinear-resizes to the target resolution, loads the whole clip into fp32 through `decord`, does not blend overlapping chunks, and writes libx264 CRF 0 at 16 fps by default. So M3 plans its own windowed frame streamer with a crossfade blend. FP16 produced black segments upstream, so bf16 only; the `api` reference mode sends frames to a third-party service, so only the local `pisasr` reference mode is allowed.

The RTX 5080 is Blackwell (sm_120) and needs PyTorch 2.7 or newer with CUDA 12.8, while SparkVSR pins torch 2.5 with cu124, which would fail with "no kernel image". This became the first spike (INQUIRY-002).

For SDR to HDR, HDRTVNet++ (MIT licence, four `.pth` files, a small per-frame CNN) was chosen. LumaFlux was rejected because it needs 27 GB and 5.3 s per 1080p frame and its weights are non-commercial; the method of arXiv 2605.14703 was rejected because no code has been released. The local FFmpeg 8.1.2 has no `zscale` or `libplacebo`, so PQ/BT.2020 math will be done in torch/numpy. Local SVT-AV1 is 4.2.0 while the server image is Alpine 3.19 with an older one, hence the version pin in the worker image (MIN-016).
